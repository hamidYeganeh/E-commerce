# کاتالوگ، مدیریت محصول و ویترین

این مرحله شامل API و رابط مدیریت دسته‌بندی، تگ، برند، ویژگی، محصول و موجودی دستی، و صفحات عمومی فهرست و جزئیات محصول است. سبد خرید، ثبت سفارش و پرداخت مرحلهٔ بعد هستند.

## استفاده

پس از راه‌اندازی DB/Redis طبق README و ساخت حساب همکار طبق [راهنمای ورود](authentication.md)، از `/staff/login` وارد شوید و MFA را تکمیل کنید.

1. در `/admin/catalog/taxonomy` برند، دسته‌بندی‌های والد/فرزند، تگ‌ها و ویژگی‌ها را ایجاد کنید.
2. برای ویژگی انتخابی، گزینه‌ها را با قالب `glass | شیشه‌ای` تعریف کنید. نوع، واحد، کلید و کلید گزینه‌های قبلی پس از ایجاد ثابت‌اند؛ عنوان‌ها و گزینه‌های جدید قابل ویرایش‌اند.
3. ویژگی را به دسته‌بندی متصل و کاربرد آن را مشخص کنید: مشخصهٔ محصول یا تنوع، اجباری و قابل فیلتر. زیردسته‌ها قواعد والد را به ارث می‌برند. یک ویژگی در دسته‌های یک محصول نمی‌تواند هم‌زمان در دو سطح محصول و تنوع باشد.
4. در `/admin/catalog/products/new` محصول را بسازید یا محصول عسل seed را از فهرست باز کنید. دسته‌بندی اصلی، توضیحات، تصاویر واقعی، قیمت تأییدشده، تنوع و مشخصات را تکمیل کنید.
5. ذخیرهٔ محصول موجودی را تغییر نمی‌دهد. حساب دارای `inventory.write` در بخش «کنترل موجودی» تعداد فیزیکی و دلیل تغییر را ثبت می‌کند.
6. وضعیت «منتشرشده» را انتخاب و ذخیره کنید. صفحهٔ `/products/<slug>` و فهرست عمومی همان داده را می‌خوانند.

قیمت فرم‌ها تومان است و با محاسبهٔ دقیق رشته/BigInt به ریال ذخیره می‌شود؛ API فیلد `priceRial` را رشته می‌گیرد و برمی‌گرداند. فیلترهای `min`/`max` در API عمومی تومان هستند. وزن برای ارسال از وزن خالص مستقل است. ویژگی استاندارد `net-weight` با وزن خالص تنوع به گرم یکسان نگه داشته می‌شود. مقدارهای عددی و ارقام فارسی یکسان‌سازی می‌شوند تا «۹۰۰» و «0900.0» دو ترکیب متفاوت محسوب نشوند.

## قواعد انتشار و تغییر

- انتشار به توضیحات، تصویر، دسته‌بندی اصلی فعال با والدهای فعال، حداقل یک تنوع فعال با قیمت مثبت، و ویژگی‌های اجباری نیاز دارد. تنوع فعال حتی در پیش‌نویس نمی‌تواند قیمت صفر داشته باشد.
- موجودی صفر مانع نمایش نیست؛ محصول «ناموجود» می‌شود. تنوع غیرفعال، پیش‌نویس و محصول بایگانی‌شده در پاسخ عمومی قرار نمی‌گیرند.
- ترکیب مشخصات تنوع‌های فعال باید یکتا باشد. شناسهٔ تنوع متعلق به محصول دیگر پذیرفته نمی‌شود. تنوع ثبت‌شده حذف نمی‌شود؛ برای حفظ ارجاع سفارش‌ها غیرفعال می‌شود.
- تغییر قواعد یا جابه‌جایی دسته‌بندی اگر محصول منتشرشده را نامعتبر کند، کل تراکنش را برمی‌گرداند. ابتدا محصول را پیش‌نویس کنید، اصلاحات را انجام دهید و دوباره منتشر کنید. حذف دستهٔ دارای فرزند یا اتصال محصول و حذف برند/تگ/ویژگی در حال استفاده رد می‌شود.
- محصول دارای `version` است؛ ویرایش قدیمی پاسخ `409 VERSION_CONFLICT` می‌گیرد. ذخیرهٔ محصول، روابط و AuditLog در یک تراکنش است. تمام نویسندگان کاتالوگ قفل advisory یکسان دارند.
- اصلاح موجودی فقط با مجوز مستقل، نسخهٔ معتبر، دلیل و `eventKey` تصادفی انجام می‌شود. تعداد کمتر از رزروشده مجاز نیست. گردش دارای مقدار مثبت/منفی، actor و سابقهٔ ممیزی است. تکرار همان درخواست دوباره موجودی را تغییر نمی‌دهد؛ استفادهٔ مجدد از شناسه با محتوای متفاوت رد می‌شود.
- پاسخ عمومی projection مشخص دارد و SKU، بارکد، تأمین‌کننده/آدرس منبع، موجودی دقیق، رزرو، نسخه و audit را منتشر نمی‌کند. APIهای مدیریت از نشست معتبر کارکنان، MFA، مجوز و Origin استفاده می‌کنند. فرم‌ها برای حالت پیش از hydration از POST استفاده می‌کنند.

## تصاویر

`POST /api/admin/catalog/media` بدنهٔ باینری تصویر می‌گیرد؛ فقط همکار دارای `catalog.write` می‌تواند بارگذاری کند. سقف ورودی ۵ مگابایت است. فایل واقعاً decode می‌شود، حداکثر ۴۰ میلیون پیکسل ورودی می‌پذیرد، به حداکثر ۲۰۰۰×۲۰۰۰ تبدیل می‌شود و metadata آن در WebP خروجی حذف می‌شود. SVG و فایل خراب رد می‌شوند. نام فایل ورودی استفاده نمی‌شود و کلید تصادفی UUID تولید می‌شود.

پیش‌فرض `MEDIA_DRIVER=local` است و فایل‌ها در `.data/media` خارج از public قرار می‌گیرند. در استقرار چند replica یا serverless از S3 استفاده کنید؛ local به volume پایدار و مشترک نیاز دارد. رسانهٔ محلی دادهٔ زمان اجرا است و در خروجی build کپی نمی‌شود؛ volume رسانه را جداگانه mount یا بازیابی کنید. تنظیمات server-only:

```dotenv
MEDIA_DRIVER=s3
MEDIA_S3_BUCKET=private-product-media
MEDIA_S3_REGION=your-region
MEDIA_S3_ACCESS_KEY_ID=...
MEDIA_S3_SECRET_ACCESS_KEY=...
# اختیاری برای سرویس سازگار با S3
MEDIA_S3_ENDPOINT=https://your-storage-endpoint
MEDIA_S3_FORCE_PATH_STYLE=true
```

Bucket باید خصوصی باشد؛ کلاینت credential یا URL مستقیم ذخیره‌سازی دریافت نمی‌کند. روت `/api/media/<key>` تصویر متصل به محصول قابل نمایش را برای مهمان ارائه می‌کند. تصویر پیش‌نویس یا تصویر تازه‌آپلودشده فقط برای کارکنان مجاز قابل مشاهده است. پاسخ رسانه و API کاتالوگ `no-store` دارد تا بایگانی و تغییرات موجودی پشت cache باقی نماند. کلیدهای جداشده فعلاً از storage پاک نمی‌شوند؛ پاک‌سازی orphanها و سیاست retention باید پیش از رشد حجم تعریف شود. اتصال واقعی S3 بدون credential محیط اجرا آزموده نشده است؛ مسیر محلی و قواعد دسترسی آزموده شده‌اند.

## صفحات و APIها

| مسیر | کاربرد |
|---|---|
| `/`, `/products` | صفحهٔ اصلی، جست‌وجو، فیلتر و صفحه‌بندی |
| `/products/[slug]` | گالری، انتخاب تنوع، قیمت، موجودی و مشخصات |
| `/categories/[slug]`, `/tags/[slug]` | فهرست محصول بر اساس دسته (همراه زیردسته‌ها) و تگ |
| `/admin/catalog` | جست‌وجوی نام/SKU، وضعیت و ورود به ویرایش |
| `/admin/catalog/products/new`, `/admin/catalog/products/[id]` | فرم محصول، تصاویر، تنوع‌ها، کنترل موجودی و آخرین تغییرات |
| `/admin/catalog/taxonomy` | ایجاد/ویرایش/حذف دسته، تگ، برند و ویژگی |
| `GET/POST /api/admin/catalog/products` | فهرست و ایجاد محصول |
| `GET/PUT /api/admin/catalog/products/[id]` | جزئیات و ذخیرهٔ کامل محصول با version |
| `GET /api/admin/catalog/lookups` | دادهٔ فرم‌ها |
| `POST /api/admin/catalog/taxonomy/[kind]` | ایجاد؛ kind یکی از categories/tags/brands/attributes |
| `PUT/DELETE /api/admin/catalog/taxonomy/[kind]/[id]` | ویرایش/حذف ساختار |
| `PUT /api/admin/inventory/[variantId]` | اصلاح موجودی، version، onHand، reason و eventKey |
| `GET /api/catalog/products`, `GET /api/catalog/products/[slug]` | projection عمومی محصولات منتشرشده |

فیلترهای عمومی: `q`, `category`, `tag`, `brand`, `min`, `max`, `stock=1`, `sort=newest|price-asc|price-desc`, `page`, `attribute=<key>`, `option=<optionId-or-value>`. هر صفحه ۱۲ محصول دارد. قیمت، موجودی و ویژگی تنوع در SQL روی همان تنوع تطبیق داده می‌شوند؛ قیمت کارت بر اساس تنوع‌های منطبق با فیلتر است. جست‌وجو parameterized است و `%`/`_` ورودی literal هستند. خواندن چندمرحله‌ای فهرست و جزئیات از snapshot تراکنشی استفاده می‌کند.

عنوان و توضیحات SEO، canonical و OpenGraph محصول پیاده شده‌اند. تگ‌ها پیش‌فرض noindex هستند. صفحه‌های فیلترشده برای جلوگیری از آدرس‌های تکراری noindex هستند. `NEXT_PUBLIC_SITE_URL` را روی دامنهٔ واقعی تنظیم کنید.

## اعتبارسنجی تحویل

`npm run test:integration` migrationهای واقعی را در PGlite موقت اجرا می‌کند و انتشار/عدم افشای پیش‌نویس، ارث ویژگی، rollback، مجوز، اصلاح موجودی، idempotency، نسخه، تداخل قیمت/موجودی، جلوگیری از تزریق SQL و پردازش فایل خراب را بررسی می‌کند. این تست جای آزمون بار و رقابت نویسندگان روی PostgreSQL واقعی را نمی‌گیرد.

علاوه بر تست‌ها، ورود MFA، انتشار از فرم محصول، ثبت موجودی و نمایش همان قیمت/موجودی در مرورگر بررسی شد. API واقعی محلی برای آپلود و مشاهدهٔ تصویر خصوصی/عمومی، فایل نامعتبر، Origin اشتباه، ورودی ناقص، نسخهٔ قدیمی و مخفی‌شدن تصویر پس از بایگانی آزموده شد. ظاهر دسکتاپ و عرض موبایل بررسی شد. همهٔ این داده‌ها آزمایشی و جدا از دیتابیس فروشگاه بودند؛ محصول اصلی seed همچنان پیش‌نویس می‌ماند.

## قواعد مشترک نمایش و خرید

ماژول `src/modules/catalog/purchase-policy.ts` قواعد مشترک محصول را برای فهرست SQL، جزئیات Prisma و بررسی سبد/ثبت سفارش ارائه می‌کند. محصول فعال باید تصویر، دستهٔ اصلی قابل نمایش و فقط دسته‌های قابل نمایش داشته باشد؛ فعال‌بودن والدها هم در محاسبهٔ دسته‌های قابل نمایش لحاظ می‌شود. محصول عمومی حداقل یک تنوع فعال با قیمت مثبت دارد و خرید برای همان تنوع انتخاب‌شده بررسی می‌شود. تمام‌شدن یا نبود موجودی، محصول را از فهرست حذف نمی‌کند؛ فیلتر موجودی و کنترل تعداد/رزرو مسئولیت جدا دارند.
