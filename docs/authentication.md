# راه‌اندازی ورود و دسترسی‌ها

## مسیرهای آماده

- `/login`: ورود و ثبت‌نام مشتری با موبایل ایران و OTP.
- `/staff/login`: ورود کارکنان با ایمیل و رمز و سپس TOTP یا کد بازیابی.
- `/admin/security`: اتصال برنامه احراز هویت، نمایش محلی QR و کدهای بازیابی، ساخت کدهای بازیابی جدید و مدیریت نشست‌ها.
- `/admin`: پنل اولیه با آمار واقعی متناسب با مجوز و نقش‌های فعلی.
- `/account`: اطلاعات حساب و نشست‌های فعال؛ خروج از حساب یا همه دستگاه‌ها.
- `/api/account/me` و `/api/account/sessions`: اطلاعات امن حساب و نشست‌ها، بدون token.
- `/api/admin/overview`: نمونه API محافظت‌شده با تأیید دومرحله‌ای؛ بخش‌های کاتالوگ/سفارش در مرحله بعد اضافه می‌شوند.

## تنظیم اولیه

```bash
cp .env.example .env
npm run infra:up
npm run db:deploy
npm run db:generate
npm run db:seed
```

در `.env` مقدار `BETTER_AUTH_URL` باید origin واقعی برنامه باشد، بدون path یا query؛ برای توسعه مثلاً `http://localhost:3000`. برای محیط production، HTTPS اجباری است. `BETTER_AUTH_SECRET` باید تصادفی، محرمانه، حداقل ۳۲ کاراکتر و در replicaها یکسان باشد. تغییر آن cookieهای امضاشده و داده‌های رمز‌شده TOTP را نامعتبر می‌کند؛ هنگام بازیابی باید همراه backup دیتابیس مدیریت شود.

برای تولید secret روی سیستم خودتان:

```bash
node -e 'console.log(require("crypto").randomBytes(48).toString("base64url"))'
```

کلید را در مخزن یا پیام چت قرار ندهید. مقدار پیش‌فرض یا مسیر ورود بدون سرویس پیامک وجود ندارد.

## کاوه‌نگار

`KAVENEGAR_API_KEY` و `KAVENEGAR_OTP_TEMPLATE` را از پنل کاوه‌نگار تنظیم کنید. الگوی lookup باید از token کد ورود استفاده کند و برای حساب فعال باشد. adapter درخواست POST به `verify/lookup.json` می‌زند و هم HTTP و هم return.status را بررسی می‌کند. timeout ده ثانیه است. خطای سرویس حاوی URL/کلید/بدنه به مشتری یا لاگ منتقل نمی‌شود.

تا تنظیم این دو مقدار، فرم ورود باز می‌شود اما ارسال پیامک با خطای قابل فهم شکست می‌خورد. هیچ کد آزمایشی، نمایش OTP در پاسخ HTTP یا چاپ کد در لاگ وجود ندارد. تست‌ها sender تزریقی درون فرایند دارند؛ runtime آن را از متغیر محیطی فعال نمی‌کند. اتصال واقعی پیامک با حساب کاربری کاوه‌نگار هنوز تأیید نشده است.

## اولین همکار فروشگاه

پس از migration و seed، در ترمینال محلی اجرا کنید:

```bash
npm run staff:create -- --email owner@example.com --name "نام مدیر" --role owner
```

اسکریپت رمز ۱۲ تا ۱۲۸ کاراکتری را به‌صورت مخفی و با تکرار می‌گیرد. رمز در آرگومان، environment، لاگ یا history قرار نمی‌گیرد. حساب تکراری یا ایمیل متعلق به مشتری را ارتقا نمی‌دهد. این دستور ابزار operator مورد اعتماد سرور است و endpoint عمومی ندارد. هیچ حساب یا رمز پیش‌فرضی seed نمی‌شود.

در `/staff/login` وارد شوید. اولین ورود فقط نشست ده‌دقیقه‌ای برای اتصال برنامه احراز هویت می‌دهد. سپس QR را با authenticator اسکن کنید، کدهای بازیابی را خارج از مرورگر ذخیره کنید و کد برنامه را تأیید کنید. تا این مرحله تکمیل نشود، پنل و API ادمین مجاز نیستند. کدهای بازیابی فقط در حافظه صفحه نگه داشته می‌شوند و پس از خروج از صفحه قابل بازیابی از UI نیستند؛ ساخت کد جدید نیاز به نشست MFA و رمز دارد.

## قرارداد امنیتی

- Better Auth مالک password hashing، امضای cookie، نشست و رمزنگاری TOTP است. Prisma schema با فیلدهای plugin نسخه نصب‌شده تطبیق داده شده است.
- شماره موبایل قبل از استفاده به `+989…` تبدیل می‌شود؛ رقم فارسی/عربی و فرمت‌های داخلی و بین‌المللی به همان حساب می‌رسند.
- OTP شش‌رقمی، با اعتبار ۱۸۰ ثانیه، فاصله ارسال ۶۰ ثانیه، حداکثر پنج تلاش و مصرف اتمی یک‌باره در Redis. فقط HMAC با secret در Redis قرار می‌گیرد؛ ردیف سازگاری Verification در DB فقط `redis-managed` دارد.
- سقف ارسال برای هر شماره پنج بار در ساعت و ده بار در روز است؛ limiter درخواست و تلاش رمز هم اتمی و مبتنی بر Redis است. Redis باید noeviction باشد؛ خطای Redis ورود را متوقف می‌کند و fallback حافظه‌ای ندارد.
- برای IP واقعی، فقط پشت reverse proxy قابل اعتماد `AUTH_IP_HEADER` را تنظیم کنید؛ proxy باید header را بازنویسی کند و origin از دسترسی مستقیم محافظت شود. بدون تنظیم header، limiter اشتراکی محافظه‌کارانه اعمال می‌شود. محدودیت شماره و ایمیل مستقل از IP برقرار است.
- نشست مشتری حداکثر چهارده روز، نشست ورود اولیه همکار ده دقیقه و نشست MFA حداکثر هشت ساعت است؛ refresh لغزان غیرفعال است. cookie در HTTPS دارای Secure و همیشه HttpOnly/SameSite=Lax است. cookieCache غیرفعال است و داده نشست و دسترسی در DB بررسی می‌شود.
- نقش به‌تنهایی مجوز پنل نیست: `authMethod=STAFF_MFA`، `mfaVerifiedAt`، فعال‌بودن کاربر و فعال‌بودن دومرحله‌ای هم بررسی می‌شوند. دادن نقش به یک نشست SMS قدیمی آن را به نشست کارکنان تبدیل نمی‌کند.
- public signup با رمز، ورود phone/password، reset رمز با SMS، غیرفعال‌کردن MFA و endpoint تولید TOTP از HTTP منتشر نیستند. فقط allowlist محدود احراز هویت در دسترس است. ساخت/بازیابی دسترسی کارکنان از مسیر operator انجام می‌شود؛ workflow دعوت/بازیابی کامل هنوز پیاده نشده است.
- هر درخواست نوشتن باید Origin دقیق خود برنامه داشته باشد؛ auth فقط JSON با حداکثر ۸ KiB می‌پذیرد. callback یا مسیر بازگشت نمی‌تواند کاربر را به دامنه بیرونی ببرد.
- بررسی صفحه یا layout جای بررسی API/سرویس را نمی‌گیرد. پیش از هر عملیات مدیریتی، `assertStaff` و permission مربوط اجرا می‌شود. داده شخصی cache عمومی ندارد.
- خروج از همه دستگاه‌ها تمام نشست‌های DB همان کاربر را حذف می‌کند؛ امکان حذف نشست کاربر دیگر با userId ارسالی وجود ندارد. غیرفعال‌کردن کاربر یا حذف نشست فوراً در guardهای سرور اثر می‌کند.

## آزمون

```bash
npm test
npm run test:integration
npm run test:auth
npm run test:queue
npm run lint
npm run build:webpack
```

تست auth به redis-server محلی نیاز دارد و یک PGlite و Redis موقت می‌سازد. به دیتابیس یا کاوه‌نگار واقعی متصل نمی‌شود. تست‌ها OTP یک‌بارمصرف و رقابت هم‌زمان، حد تلاش، منع تزریق دسترسی، onboarding و challenge کارکنان، کد بازیابی، تغییر زنده مجوز، ابطال نشست، Origin و adapter کاوه‌نگار را بررسی می‌کنند.

طراحی تصویری 12ui در این اجرا به سرویس hosted دسترسی پیدا نکرد؛ UI این مرحله فرم‌های ساده و راست‌چین است. این بخش طراحی کامل ویترین یا پنل مدیریت محصول نیست.

منابع: [Better Auth phone number](https://better-auth.com/docs/plugins/phone-number)، [Better Auth 2FA](https://better-auth.com/docs/plugins/2fa)، [SDK رسمی کاوه‌نگار](https://github.com/kavenegar/kavenegar-node).
